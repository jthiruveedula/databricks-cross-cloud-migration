# MLflow

MLflow experiment tracking is workspace-local — experiments, runs, metrics, and logged artifacts don't move automatically when you stand up a target workspace. This page covers experiment/run migration; [model registry](/ml/model-registry) covers registered models specifically, and [serving and artifacts](/ml/serving-and-artifacts) covers what happens after a model is deployed.

<Callout client:visible variant="warning" title="Run history has no built-in export/import">
  Unlike Unity Catalog tables, there is no first-class "clone this experiment to another workspace" operation. Migrating MLflow history means reading it via the API on source and re-logging it on target — budget real engineering time for this, not just a config change.
</Callout>

## What migrates and how

| Asset | Migration approach |
|---|---|
| Experiments | Recreate by name in target; map source experiment ID → target experiment ID |
| Runs (params, metrics, tags) | Read via `MlflowClient` on source, re-log via `mlflow.start_run()` on target |
| **Metric history** | **Not in `run.data.metrics`** — that holds only the latest value per key. Fetch `get_metric_history` per metric |
| Logged artifacts (models, plots, files) | Download from source artifact store, re-upload to target artifact store |
| Run lineage / parent-child runs | Re-set `mlflow.parentRunId` **remapped through the run ID map** — the source parent ID means nothing in the target, and parents must migrate before their children |
| **Source → target run ID map** | Nothing produces it for you, and [model registry](/ml/model-registry) re-registration needs it |

<Callout client:visible variant="warning" title="The naive version of this script silently loses training curves and stops at 1000 runs">
  Two defaults make a script that looks correct on a demo experiment and quietly under-delivers on a real one:

  - **`run.data.metrics` is the latest value per key, not the series.** Re-logging from it turns a 200-epoch training curve into a single point. The history lives behind `get_metric_history(run_id, key)`, and re-logging needs the original `step` and `timestamp` or the x-axis is still lost.
  - **`search_runs` returns at most 1000 runs** and pages via `page_token`. An experiment with 5,000 runs migrates 1,000 of them and reports success.

  Both fail silently — the target has runs, the counts just do not match, and nobody compares them unless the validation step below is actually run.
</Callout>

## Migration script pattern

<CodeBlock client:visible language="python" filename="migrate_mlflow_runs.py" code={`import mlflow
from mlflow.tracking import MlflowClient

source_client = MlflowClient(tracking_uri=SOURCE_TRACKING_URI)
mlflow.set_tracking_uri(TARGET_TRACKING_URI)

experiment = source_client.get_experiment_by_name("churn_model")
target_exp_id = mlflow.create_experiment("churn_model")

def all_runs(experiment_id):
    """search_runs caps at 1000 -- page or silently lose the rest."""
    token = None
    while True:
        page = source_client.search_runs(
            [experiment_id], max_results=1000, page_token=token
        )
        for run in page:
            yield run
        token = getattr(page, "token", None)
        if not token:
            break

run_id_map = {}
for run in all_runs(experiment.experiment_id):
    with mlflow.start_run(experiment_id=target_exp_id) as target_run:
        run_id_map[run.info.run_id] = target_run.info.run_id

        for key, value in run.data.params.items():
            mlflow.log_param(key, value)

        # run.data.metrics holds only the LATEST value per key. Replay the
        # full series, preserving step and timestamp, or the curve is lost.
        for key in run.data.metrics:
            for point in source_client.get_metric_history(run.info.run_id, key):
                mlflow.log_metric(key, point.value, step=point.step, timestamp=point.timestamp)

        for key, value in run.data.tags.items():
            if not key.startswith("mlflow."):  # mlflow.* tags are system-managed
                mlflow.set_tag(key, value)

        # ...with one exception. parentRunId is an mlflow.* tag, so the filter
        # above drops it and the nested-run structure collapses. Re-set it,
        # REMAPPED -- the source parent id means nothing in the target.
        parent = run.data.tags.get("mlflow.parentRunId")
        if parent and parent in run_id_map:
            mlflow.set_tag("mlflow.parentRunId", run_id_map[parent])

        local_path = source_client.download_artifacts(run.info.run_id, ".")
        mlflow.log_artifacts(local_path)

# Hand this to model-registry migration: re-registering a model version needs
# the MIGRATED run id, not the source one.
print(run_id_map)
`} />

## Artifact store URI portability

<Callout client:visible variant="warning" title="Re-uploading artifact bytes doesn't fix embedded paths">
  A model's `MLmodel` file and `conda.yaml`/`requirements.txt` can embed scheme-specific paths (`dbfs:/`, `s3://`, `mlflow-artifacts:/`) inside custom pyfunc wrappers, code paths, or artifact references — not just as the top-level artifact URI. Re-running `mlflow.log_artifacts()` on the target moves the bytes, but any code inside the model that hardcodes a source-scheme path will still reference the wrong location at inference time.
</Callout>

Before migrating a run's artifacts, check for hardcoded paths beyond the top-level artifact URI:

- Custom `pyfunc` wrappers that read auxiliary files (vocab files, lookup tables) via an absolute path rather than a path relative to the artifact root.
- Conda/pip requirements files referencing an internal package index by a source-workspace-specific URL.
- Any `code_path` entries in `log_model()` calls — these are copied as-is and can themselves contain source-path assumptions.

Re-log the model with `mlflow.pyfunc.log_model(..., artifacts={...})` using artifact-relative references, rather than trusting a straight file copy, whenever the model's code touches paths beyond what MLflow manages automatically.

## Deciding what to actually migrate

<Callout client:visible variant="tip" title="Not every run deserves migration">
  Full experiment history can be enormous, and most exploratory runs have no lasting value. Migrate the runs that fed production models (traceable via the [model registry](/ml/model-registry) lineage) and any runs required for compliance/audit purposes; archive or leave the rest on source rather than paying to replicate everything.
</Callout>

## Validation

- Confirm migrated runs' metrics and params exactly match source for a sample of runs, not just that "a run exists."
- Verify parent-child run relationships (e.g. hyperparameter sweep parent runs and their child runs) survived the migration correctly.
- Confirm logged model artifacts can actually be loaded and produce the same predictions as the source-logged model on a fixed test input.

## Rollback

MLflow tracking data is additive; if a migration script produces bad runs in target, delete them and re-run rather than treating it as an environment rollback. Source tracking data stays untouched and available as the reference copy throughout.

## Automation opportunity

- Parameterize the migration script by experiment name/tag so it can be re-run incrementally as new runs accumulate during a phased migration, rather than a single one-time bulk copy.
- Skip re-uploading artifacts whose content hash already matches an existing target artifact, to avoid redundant transfer on re-runs.
