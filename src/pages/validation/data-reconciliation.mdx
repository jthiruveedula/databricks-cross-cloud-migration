# Data reconciliation

Data reconciliation proves that target data matches source data within agreed tolerances. It is the most critical validation activity before cutover.

## Reconciliation dimensions

| Dimension | Method | Tolerance |
|-----------|--------|-----------|
| Row count | `COUNT(*)` per table | 0% |
| Column-level checksum | Hash aggregate by column | 0% |
| File count | List files in storage | 0% |
| File size / checksum | Cloud-native checksums | 0% |
| Schema | Compare column names, types, nullability | Exact match |
| Partitions | Compare partition values and counts | 0% |
| Primary/unique keys | Verify uniqueness constraints | 0% |
| Delta table history | `DESCRIBE HISTORY` on target vs. source | Non-zero — see below |

<Callout client:visible variant="warning" title="0% tolerance assumes a quiesced table — most tables during migration are not">
  Every row above is exact-match by default, and that is the right default. It only holds for a table that is genuinely frozen for the comparison window: a batch table inside a freeze, or a static reference table. A table still receiving writes during the compare — near-real-time ingestion, a streaming table, or a table with floating-point columns where two computationally-equivalent values are not bit-identical — needs the tolerance-based approach below instead of a widened "close enough" percentage bolted onto the exact-match query.
</Callout>

## Row-count and checksum query

<Callout client:visible variant="warning" title="A per-row hash is not a checksum — it has to be aggregated">
  Hashing each row and eyeballing (or `ORDER BY`-ing) the list does not scale past a handful of rows, and it gives you nothing to diff against the target in one shot. Aggregate the per-row hashes with a commutative, order-independent operation — `SUM()` over `xxhash64()` — so two tables compare with a single `COUNT` and a single 8-byte sum, regardless of table size or row order. This is the same principle behind SQL Server's `CHECKSUM_AGG` and the Merkle-tree-style anti-entropy checks used for cross-region replica repair: verification cost stays O(1) to transfer, not O(n) rows.
</Callout>

<CodeBlock client:visible language="sql" filename="reconcile.sql" code={`-- Reconcile row count
SELECT 'source' AS env, COUNT(*) AS cnt FROM source_catalog.schema.table
UNION ALL
SELECT 'target' AS env, COUNT(*) AS cnt FROM target_catalog.schema.table;

-- Column-level checksum: one order-independent number per side, not one hash per row
SELECT 'source' AS env, COUNT(*) AS cnt, SUM(xxhash64(col1, col2, col3)) AS agg_hash
FROM source_catalog.schema.table
UNION ALL
SELECT 'target' AS env, COUNT(*) AS cnt, SUM(xxhash64(col1, col2, col3)) AS agg_hash
FROM target_catalog.schema.table;

-- Only if agg_hash disagrees: fall back to a row-level diff to isolate the mismatch
SELECT * FROM source_catalog.schema.table
EXCEPT
SELECT * FROM target_catalog.schema.table;`} />

## Volume reconciliation

<Callout client:visible variant="warning" title="A dry-run sync diffs by size and modified time, not content">
  `aws s3 sync --dryrun` and `gsutil rsync -n` below tell you file *counts* line up — they do not prove the bytes match. Two files can share a size and a coincidental mtime and still differ. For anything where content integrity actually matters (not just "did the copy run"), compute and compare a real content hash.
</Callout>

<CodeBlock client:visible language="bash" code={`# AWS example: compare file counts and total size (not content)
aws s3 sync s3://source-bucket/path s3://target-bucket/path --dryrun

# GCP example (not content)
gsutil -m rsync -r gs://source-bucket/path gs://target-bucket/path -d -n

# Content hash, per file -- the check that actually proves the bytes match.
# S3's ETag is an MD5 only for single-part uploads; multipart uploads (the
# default above a threshold) produce a different, non-portable ETag, so it
# cannot be compared directly against a GCS/ADLS hash. Compute your own hash
# on both sides instead of trusting the cloud-native one to be comparable
# across providers.
aws s3api get-object-attributes --bucket source-bucket --key path/file.parquet \\
  --object-attributes Checksum --query 'Checksum.ChecksumSHA256' --output text
gsutil hash -h gs://target-bucket/path/file.parquet   # prints CRC32C and MD5

# Cross-cloud-safe fallback: stream both files through the same hash function
# so the comparison never depends on a provider's native checksum algorithm.
aws s3 cp s3://source-bucket/path/file.parquet - | sha256sum
gsutil cp gs://target-bucket/path/file.parquet - | sha256sum`} />

<Callout client:visible variant="tip" title="ML artifacts, feature stores, and embeddings are volumes too">
  Model weights, feature-store Parquet files, and vector-embedding files have no row-count or SQL checksum to lean on — they reconcile exactly like any other volume content: file-count-and-size as the cheap first pass, `sha256sum` as the check that actually proves nothing was corrupted or truncated in transit. Treat "it's an ML artifact" as a reason to be more careful here, not a reason this section doesn't apply.
</Callout>

## Tolerance-based reconciliation, for tables that can't be quiesced

The exact-match approach above assumes a stable snapshot on both sides. Two situations break that assumption, and each needs a different fix — not a looser percentage on the same query.

<Accordion client:visible items={[
  {
    title: 'Streaming tables and DLT pipelines — reconcile the checkpoint, not a live row count',
    content: 'A table still being written by a Structured Streaming or DLT pipeline never holds still long enough for a row count on both sides to agree, even a millisecond apart. Reconcile the input offset instead of the output row count: compare the source pipeline\'s last-committed checkpoint/offset against what the target pipeline has consumed as of a specific point in time, using `DESCRIBE HISTORY` on the streaming table\'s Delta log to read the checkpoint metadata for each side, or the pipeline\'s own checkpoint location if it is not Delta-backed. Two pipelines built from the same source and caught up to the same offset are reconciled, even if a row count taken moments apart would disagree.'
  },
  {
    title: 'Floating-point columns — compare with an epsilon, not equality',
    content: 'Two computationally-equivalent floating-point values are not always bit-identical after passing through different compute engines or codepaths — `xxhash64` hashes the bit pattern, so a value that is numerically equal but bit-different still fails the exact aggregate-hash check. For tables with floating-point columns, run a separate numeric-tolerance comparison: `SELECT COUNT(*) FROM source_catalog.schema.table s JOIN target_catalog.schema.table t ON s.id = t.id WHERE abs(s.amount - t.amount) > 0.0001` (or your agreed epsilon). A nonzero result here is a real finding; a nonzero result from the bit-exact hash on a float column, on its own, is not conclusive of anything until this check has run.'
  },
  {
    title: 'Sampling, only when full comparison is genuinely infeasible',
    content: 'For a table too large to checksum in the maintenance window even with the aggregate-hash approach, a statistical sample (row count agreement plus a hash comparison over a deterministic, seeded sample of partitions or key ranges) is a documented, signed-off exception — not a default. Record the sample size, the selection method, and who approved treating a sample as sufficient evidence for that specific table; an unstated sampling policy that quietly became the norm for large tables is a compliance and reconciliation gap discovered later, not a shortcut that saved time.'
  }
]} />

## Delta table history reconciliation

<CodeBlock client:visible language="sql" filename="describe_history.sql" code={`DESCRIBE HISTORY source_catalog.schema.table;
DESCRIBE HISTORY target_catalog.schema.table;`} />

<Callout client:visible variant="warning" title="Target history will never match source history — that's expected, not a bug">
  `CLONE` (deep or shallow) never copies Delta Lake table history. Even a correctly-run `DEEP CLONE` produces a target whose `DESCRIBE HISTORY` starts fresh at its own `CLONE` operation — it will not contain source's pre-migration versions, and time travel against those versions will fail once source is decommissioned. Don't reconcile by comparing history *row-for-row*; instead confirm:

  - Target's most recent operation is `CLONE` (not `WRITE`/`CREATE TABLE AS SELECT`/`STREAMING UPDATE`) — the tell for a raw sync or CTAS copy, which additionally risk a `_delta_log` inconsistent with the copied data files.
  - `operationParameters` on that `CLONE` row references the correct source table and version.
  - Any table where pre-cutover time travel is a real requirement has that requirement satisfied separately — via `cloneAtVersion`/`cloneAtTimestamp` snapshots taken before cutover, or a source retention plan — per [known limitations](/troubleshooting/known-limitations) and the [FAQ](/troubleshooting/faq). Row counts and checksums matching does not mean history was preserved; this is a distinct check.
</Callout>

## Handling mismatches

1. Identify the partition or file causing the mismatch.
2. Re-run the copy or sync for that subset.
3. Investigate if the mismatch is due to ongoing source changes during sync.
4. Document the resolution before signing off.

<Callout client:visible variant="warning" title="Do not ignore small mismatches">
  Even a single-row mismatch can indicate a bug in the migration logic or a permissions issue. Treat every mismatch as a severity-2 finding until explained.
</Callout>

## Validation

- Reconcile every migrated table and volume.
- Run reconciliation after final sync and again after cutover.
- Store reconciliation reports with timestamps.

## Rollback

If reconciliation fails beyond tolerance, halt cutover and re-sync. Do not proceed until all severity-1 findings are resolved.

## Automation opportunity

- `dbxmig reconcile --live` runs this exact `SUM(xxhash64(...))` query against both source and target warehouses and blocks on any row-count or hash mismatch — see the [automation toolkit](/templates/automation-toolkit). It's scoped to tables that already passed metadata reconciliation (object counts, schema match); it does not yet cover volumes/files or clone provenance from the CLI.
- Run reconciliation queries via a Databricks job and store results in a Delta table for a historical trend, not just a pass/fail at cutover.
- Generate alerts when any table exceeds tolerance.
