# Secrets and KMS

Secret scopes do not migrate. Neither do encryption keys. Both are recreated in the target, and the interesting work is not the recreation — it is knowing **which secret is used by what, and where its authoritative value comes from.**

That map is a discovery deliverable, not a cutover task, because it depends on people who may have left by the time anyone needs it.

## The two backends behave completely differently

Almost every mistake on this page comes from treating these as one thing.

| | Databricks-backed scope | Key Vault-backed scope |
|---|---|---|
| Where the value lives | Encrypted store owned by Databricks | **In your cloud vault** — Databricks holds a pointer |
| Can you read the value back? | **Yes**, via the Secrets API with `READ` | Not through Databricks — go to the vault |
| Cross-cloud portability | Recreate the scope, re-put the values | **None.** The backing vault is a cloud resource |
| Target equivalent | Same thing in the target workspace | Rethink: target-cloud vault, or Databricks-backed |

<Callout client:visible variant="warning" title="You can export Databricks-backed secrets. That is not a reason to.">
  A caller with `READ` can retrieve values through `secrets get-secret`, so a scripted export/import is technically available. It is also a decision to decrypt every production credential into a file on somebody's machine, which many organisations prohibit outright.

  Default to **re-sourcing from the system of record** that issued each secret, and treat migration as a rotation event. Reserve the export path for secrets that genuinely have no other source, and handle the output like the credential dump it is.
</Callout>

## Step 1 — Build the dependency map

Names, not values. This is the artifact everything else depends on.

<CodeBlock client:visible language="bash" filename="inventory-secrets.sh" code={`# Scopes, with their backend type -- the column that decides the strategy
databricks secrets list-scopes --output json \\
  | jq -r '.scopes[] | [.name, .backend_type] | @tsv'

# Key names per scope. Never the values.
for scope in $(databricks secrets list-scopes --output json | jq -r '.scopes[].name'); do
  databricks secrets list-secrets "$scope" --output json \\
    | jq -r --arg s "$scope" '.secrets[] | [$s, .key] | @tsv'
done`} />

Then find the references, which is the half people skip:

<CodeBlock client:visible language="bash" filename="find-references.sh" code={`# Cluster specs, job definitions, and pipeline configs
dbxmig -c migration.yaml crossrefs -w workspace.json --csv crossrefs.csv

# ...and notebook and repo source, with a file and line number
dbxmig -c migration.yaml crossrefs -w workspace.json -s ./workspace-export`} />

That reports both spellings — `dbutils.secrets.get(scope=..., key=...)` and the `{{secrets/scope/key}}` form used in Spark conf and job parameters — and flags any reference to a scope that is not in the inventory. See [asset inventory](/discovery/asset-inventory).

<Callout client:visible variant="tip" title="A referenced scope that does not exist in the inventory is the finding, not a bug">
  It usually means the scope lives in a different workspace, or was deleted while a job still references it and that job has been failing quietly. Either way it is a question for an owner before cutover, not after.
</Callout>

## Step 2 — Decide per secret, then record the decision

| Situation | Do |
|---|---|
| Issued by a system of record (vault, CI, IdP, partner portal) | **Re-issue from there.** The best case |
| Cloud credential for the source cloud | **Does not migrate** — the target needs a target-cloud identity |
| Third-party API key | **Rotate.** Migration is the excuse to do it properly |
| Nobody knows where it came from | Escalate now — this is the one that stops a cutover |
| Genuinely no other source, low sensitivity | Export and re-put, with controls |

<Callout client:visible variant="warning" title="Some secrets should not exist in the target at all">
  A storage account key or an access key for source-cloud storage has no place in the target — that access is a [storage credential](/security/target-storage-credentials) now, not a secret. Migrating it faithfully recreates a credential that should be deleted. Check the list for anything that Unity Catalog should own instead.
</Callout>

## Step 3 — Create target scopes

<Accordion client:visible items={[
  {
    title: 'Databricks-backed — the portable default',
    content: 'databricks secrets create-scope <name> creates a Databricks-backed scope in the target workspace, then databricks secrets put-secret <scope> <key> puts each value. This is the right default for a cross-cloud move because it carries no cloud dependency. Set scope ACLs immediately: a scope is created with MANAGE for its creator and nothing else, so every job service principal needs an explicit READ grant or it fails at first run.'
  },
  {
    title: 'Vault-backed — only when the target cloud vault is the system of record',
    content: 'A Key Vault-backed scope points Databricks at Azure Key Vault. There is no equivalent backing for AWS Secrets Manager or GCP Secret Manager as a Databricks scope backend, so "Key Vault-backed scope in AWS" is not a thing to plan for. Moving off Azure means those scopes become either Databricks-backed, or your application reads the target cloud vault directly rather than through a scope. Decide which during design -- it changes application code, not just configuration.'
  }
]} />

<CodeBlock client:visible language="bash" filename="create-target-scopes.sh" code={`databricks secrets create-scope prod-etl

# Values come from the system of record, not from a source export.
databricks secrets put-secret prod-etl partner_api_token \\
  --string-value "$(vault kv get -field=token secret/partner)"

# ACLs are not optional -- the scope is invisible to everyone else until set.
databricks secrets put-acl prod-etl svc-etl-prod-gcp READ
databricks secrets put-acl prod-etl data-platform-admins MANAGE`} />

<Callout client:visible variant="warning" title="Scope ACLs are the step that gets forgotten, and it fails at first run">
  Creating the scope and putting the values is not enough. Until a principal holds `READ` on the scope, `dbutils.secrets.get` raises a permission error — and because it happens inside a job at execution time rather than at deploy time, a bundle can deploy cleanly and every job still fail. Grant to the **job's run-as identity**, which is often a service principal and not the person testing.
</Callout>

## Step 4 — Sequence it against cutover

Secrets have to exist before the first target workload runs, and rotated secrets have to change on both sides at a moment you control.

| When | Do |
|---|---|
| Discovery | Dependency map complete; every secret has an owner and a source |
| Foundation | Target scopes created, ACLs granted, non-rotating secrets populated |
| Pilot | One real job proves resolution end to end with its own run-as identity |
| Pre-cutover | Rotating secrets re-issued in the target; source values still live |
| Cutover | Third-party keys rotated where the old value must stop working |
| Hypercare | Source secrets revoked once nothing reads them |

<Callout client:visible variant="tip" title="Do not rotate a shared third-party key at the same moment you cut over">
  If source and target both use one API key and you rotate it at cutover, you have changed two variables at once — and if anything breaks you cannot tell which. Rotate before or after, on a day when it is the only change.
</Callout>

## Customer-managed keys

| Source | Target |
|--------|--------|
| Azure Key Vault CMK | AWS KMS customer-managed key |
| AWS KMS CMK | Azure Key Vault key or GCP Cloud KMS key |
| GCP Cloud KMS CMEK | AWS KMS or Azure Key Vault key |

Plan key rotation and data re-encryption:

- If data is copied to target storage, encrypt it with the target CMK at write time.
- For blue-green, rotate target keys after cutover and disable old key versions per policy.

## Personal access token retirement

<Callout client:visible variant="tip" title="Use OAuth and service principals">
  Replace personal access tokens with OAuth service principals and managed identities. PATs tied to individual users do not survive identity changes and are harder to audit.
</Callout>

## Validation

- Every secret reference found by the cross-reference scan resolves in the target — including references inside notebook source, not just job configuration.
- Resolution tested with the **job's run-as identity**, not an admin who holds `MANAGE` on everything.
- No secret in the target is a source-cloud storage credential that Unity Catalog should own instead.
- Key access and rotation rehearsed in a non-production target workspace.
- Cloud KMS policy allows the target compute identity to decrypt.

## Rollback

A missing or wrong secret fails the job that needs it, loudly and immediately — which makes this one of the safer things to get wrong. Keep the source scopes intact and readable until hypercare ends so a value can be re-checked, and keep the dependency map current enough to answer "what else uses this key" before rotating anything.

The irreversible case is revoking a third-party credential at the provider: the old value stops working everywhere, including the source you were planning to fall back to. Sequence those separately from cutover.

## Automation opportunity

- `dbxmig workspace` inventories scopes and key names — never values — and `dbxmig crossrefs --source` finds both reference spellings across configuration and code, with a file and line. See the [automation toolkit](/templates/automation-toolkit).
- Define target scopes and ACLs as [Terraform](/templates/terraform-patterns), so the ACL grant cannot be the step someone forgets.
- Add a post-deploy smoke job that resolves one key per scope as the run-as identity. It is a few seconds and it catches the ACL gap before a business job does.
