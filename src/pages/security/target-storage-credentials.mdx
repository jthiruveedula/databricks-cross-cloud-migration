# Target storage credentials

[Metastore migration](/governance/metastore-migration) opens with a step it says cannot be automated: the storage credential. This is that step, in full.

It is the first thing you build in the target and the thing everything else waits on — no external location, no catalog managed location, no table, no clone, until this validates. It is also the step most likely to need somebody who is not on the migration team, which is why it belongs in week one rather than in the sprint before cutover.

<Callout client:visible variant="warning" title="A cloud identity is not translated, it is designed">
  There is no mapping from an Azure managed identity to a GCP service account. Every construct differs — how trust is established, who may grant it, what the blast radius of over-granting is. Approach this as a design task against the target cloud's model, using the source only as a list of *what access is needed*, never as a template for how to express it. See [IAM mapping](/security/iam-mapping) for the construct-level comparison.
</Callout>

## The shape, in all three clouds

Whatever the cloud, four things happen in the same order, and the ordering is not negotiable:

1. **Create a cloud identity** that Databricks can assume.
2. **Grant it on the storage**, scoped as narrowly as the estate allows.
3. **Register it in Unity Catalog** as a storage credential.
4. **Validate it for read *and* write**, then build external locations on top.

Step 4 is not a formality. The most common day-one failure is a credential that validates for `LIST` and fails on `WRITE`, because the storage-side grant was read-only — and the error names the Databricks object, not the missing cloud role.

## Azure — Access Connector and managed identity

<Callout client:visible variant="tip" title="Two different Azure roles, usually two different people">
  Creating the access connector needs **Contributor or Owner on the resource group**. Granting it on the storage account needs **Owner or User Access Administrator on the storage account**. In most enterprises those are separate people with separate approval paths, and discovering that on the day is how this step turns into a week. Line both up before you start.
</Callout>

<CodeBlock client:visible language="bash" filename="azure-credential.sh" code={`RG=nwr-prod-rg
LOCATION=eastus
CONNECTOR=nwr-uc-connector
STORAGE=nwrprodgen2

# 1. Access connector -- a first-party Azure resource. Deploys with a
#    system-assigned managed identity by default.
az databricks access-connector create \\
  --resource-group "$RG" \\
  --name "$CONNECTOR" \\
  --location "$LOCATION" \\
  --identity-type SystemAssigned

CONNECTOR_ID=$(az databricks access-connector show \\
  --resource-group "$RG" --name "$CONNECTOR" --query id -o tsv)
PRINCIPAL_ID=$(az databricks access-connector show \\
  --resource-group "$RG" --name "$CONNECTOR" --query identity.principalId -o tsv)

# 2. Grant on storage. Scope to the storage account, or to a single container
#    if the estate justifies the extra objects to manage.
az role assignment create \\
  --assignee-object-id "$PRINCIPAL_ID" \\
  --assignee-principal-type ServicePrincipal \\
  --role "Storage Blob Data Contributor" \\
  --scope "$(az storage account show -g "$RG" -n "$STORAGE" --query id -o tsv)"

echo "Access Connector ID for the storage credential: $CONNECTOR_ID"`} />

<CodeBlock client:visible language="sql" filename="azure-credential.sql" code={`-- 3. Register it. The identifier is the access connector's RESOURCE ID,
--    not the managed identity's principal id -- a very common mix-up.
CREATE STORAGE CREDENTIAL nwr_uc_azure
  WITH AZURE_MANAGED_IDENTITY (
    ACCESS_CONNECTOR_ID = '<paste $CONNECTOR_ID>'
  )
  COMMENT 'Access connector for nwrprodgen2';`} />

For a **user-assigned** identity instead of system-assigned — which you want when the same identity must outlive the connector or be shared — attach it to the connector and supply both the connector ID and the managed identity resource ID.

## AWS — the self-assuming role, and its chicken-and-egg

This is the fiddliest of the three, and the awkwardness is inherent rather than incidental.

<Callout client:visible variant="warning" title="A role copied from a pre-2023 setup will be blocked outright">
  AWS changed IAM trust semantics on **30 June 2023** to require roles to explicitly self-trust for `sts:AssumeRole`, and Databricks requires storage-credential roles to be **self-assuming** as a result. Since **20 January 2025** Databricks blocks existing storage credentials whose roles are not self-assuming.

  For a migration this matters twice: a new target role must be built self-assuming from the start, and if you are lifting an IAM policy from an older source estate as a template, that template is out of date and will fail validation rather than degrade quietly.
</Callout>

The circular dependency: the trust policy must contain the storage credential's **external ID**, but the external ID does not exist until the storage credential is created — and the storage credential cannot be created without the role. Databricks resolves it with a placeholder and a second pass. Expect three steps, not one.

<Accordion client:visible items={[
  {
    title: 'Pass 1 — create the role with a placeholder external ID',
    content: 'Create the IAM role with a trust policy that names the Databricks master role as principal and sets the external ID condition to the placeholder value 0000. Attach the S3 access policy at the same time. The role now exists and can be referenced, but it will not yet validate.'
  },
  {
    title: 'Pass 2 — create the storage credential, and read back its external ID',
    content: 'Create the storage credential in Unity Catalog pointing at the role ARN. Databricks generates an external ID for that credential. Copy it. This is the value the placeholder was standing in for.'
  },
  {
    title: 'Pass 3 — update the trust policy with the real external ID, and make it self-assuming',
    content: 'Replace 0000 with the real external ID, and add the role\'s OWN ARN to the Principal alongside the Databricks master role ARN. That second entry is what makes the role self-assuming. Then validate the credential: if the "Self Assume Role" check fails, the trust policy is still wrong -- it is almost always the missing self-reference rather than the external ID.'
  }
]} />

<CodeBlock client:visible language="json" filename="trust-policy-final.json" code={`{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::<DATABRICKS-MASTER-ACCOUNT>:role/<DATABRICKS-MASTER-ROLE>",
          "arn:aws:iam::<YOUR-AWS-ACCOUNT-ID>:role/nwr-uc-s3-role"
        ]
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "<STORAGE-CREDENTIAL-EXTERNAL-ID>"
        }
      }
    }
  ]
}`} />

The second ARN in that list is the role itself. That is the self-assumption, and it is the line people leave out.

<CodeBlock client:visible language="bash" filename="aws-credential.sh" code={`# Pass 1 -- placeholder external id
aws iam create-role --role-name nwr-uc-s3-role \\
  --assume-role-policy-document file://trust-policy-placeholder.json
aws iam put-role-policy --role-name nwr-uc-s3-role \\
  --policy-name uc-s3-access --policy-document file://s3-access.json

# Pass 2 -- create the credential in Databricks, then read its external id
databricks storage-credentials create --json '{
  "name": "nwr_uc_aws",
  "aws_iam_role": {"role_arn": "arn:aws:iam::<ACCT>:role/nwr-uc-s3-role"}
}'
databricks storage-credentials get nwr_uc_aws \\
  --output json | jq -r '.aws_iam_role.external_id'

# Pass 3 -- put the real external id in, add the self-reference, re-validate
aws iam update-assume-role-policy --role-name nwr-uc-s3-role \\
  --policy-document file://trust-policy-final.json`} />

## GCP — the generated service account

The inverse of AWS: Databricks creates the identity, and you grant it. Nothing to design on the trust side, which makes this the least error-prone of the three.

<CodeBlock client:visible language="sql" filename="gcp-credential.sql" code={`-- 1. Create the credential first. Databricks generates a service account
--    and returns its email -- that email is the thing you grant.
CREATE STORAGE CREDENTIAL nwr_uc_gcp
  WITH DATABRICKS_GCP_SERVICE_ACCOUNT
  COMMENT 'UC access to nwr-prod-* buckets';

-- Read back the generated service account email.
DESCRIBE STORAGE CREDENTIAL nwr_uc_gcp;`} />

<CodeBlock client:visible language="bash" filename="gcp-grant.sh" code={`SA=<generated-service-account-email-from-DESCRIBE>

# 2. Grant on the BUCKET, not the project. Project-level grants are the single
#    most common over-permission in a GCP Databricks estate.
#
#    Read-write access needs both of these roles -- Storage Object Admin alone
#    is not sufficient, because Unity Catalog also needs bucket-level metadata.
gcloud storage buckets add-iam-policy-binding gs://nwr-prod-managed \\
  --member="serviceAccount:\${SA}" \\
  --role=roles/storage.objectAdmin

gcloud storage buckets add-iam-policy-binding gs://nwr-prod-managed \\
  --member="serviceAccount:\${SA}" \\
  --role=roles/storage.legacyBucketReader`} />

For a location that should never be written to — an archive, or a source bucket you are reading during migration — mark the storage credential **read-only** in Unity Catalog rather than relying on the IAM roles alone. Defence in depth: the credential flag stops Databricks from attempting a write, and the bucket policy stops it from succeeding if something bypasses the flag.

## Validate before building anything on top

<CodeBlock client:visible language="python" filename="validate.py" code={`from databricks.sdk import WorkspaceClient

w = WorkspaceClient()

# Validate the credential itself -- including, on AWS, the self-assume check.
print(w.storage_credentials.validate(storage_credential_name="nwr_uc_gcp"))

# Then validate the external location, which exercises the actual path.
print(w.external_locations.validate(external_location_name="nwr_managed"))`} />

Read every operation in the result, not the overall verdict. A credential can report success on `LIST` and `READ` and fail `WRITE`, and a migration will not discover that until the first `DEEP CLONE` — by which point the failure looks like a Delta problem.

<Callout client:visible variant="tip" title="Validate with a path that is representative, not a path you just created">
  Validating against an empty prefix you made for the test proves the credential works on an empty prefix you made for the test. Point it at a real location — one with the actual directory depth and, on Azure, an HNS container rather than a flat one, so the check exercises what production will.
</Callout>

## Then, and only then, the external locations

<CodeBlock client:visible language="sql" filename="external-locations.sql" code={`CREATE EXTERNAL LOCATION IF NOT EXISTS nwr_managed
  URL 'gs://nwr-prod-managed/'
  WITH (STORAGE CREDENTIAL nwr_uc_gcp)
  COMMENT 'Managed data root for prod catalog';

-- Least privilege from the start: almost nobody should hold direct access to
-- an external location. Tables and volumes are the intended access path.
GRANT READ FILES ON EXTERNAL LOCATION nwr_managed TO \`data-platform-admins\`;
GRANT CREATE EXTERNAL TABLE ON EXTERNAL LOCATION nwr_managed
  TO \`data-platform-admins\`;`} />

<Callout client:visible variant="warning" title="Broad grants on an external location bypass table-level governance">
  `READ FILES` on an external location lets the grantee read every file underneath it, including files behind tables whose row filters and column masks would otherwise apply. It is a governance hole that no table grant closes. Keep it to the platform team, and route everyone else through tables and volumes — see [external locations and volumes](/governance/external-locations-and-volumes).
</Callout>

## Common failures, and what they actually mean

| Symptom | Cause |
|---|---|
| Credential validates `LIST`, fails `WRITE` | Storage grant is read-only — wrong role, not wrong credential |
| AWS: "Self Assume Role" check fails | Role's own ARN missing from its trust policy Principal |
| AWS: works today, blocked later | Non-self-assuming role from an older template |
| Azure: connector not found | Supplied the managed identity principal id instead of the **access connector resource id** |
| Azure: role assignment refused | Grantor lacks Owner or User Access Administrator on the storage account |
| GCP: permission denied on write | Granted at project level with a viewer role, or missing `legacyBucketReader` |
| Everything validates, clone still fails | Firewall on the storage account — for serverless that means [NCC stable IPs](/security/serverless-networking), not your VNet |

That last row is worth dwelling on: a correct credential and a storage firewall that does not know about serverless produce identical-looking failures, and teams spend days re-creating credentials that were fine.

## Validation

- Credential validates for read **and** write, against a representative path.
- On AWS, the self-assume check passes explicitly.
- External locations created and validated on top of the credential.
- Direct external-location grants limited to the platform team.
- A real workload — one `DEEP CLONE` of a small table — succeeds end to end before the bulk run is scheduled.

## Rollback

Fully reversible and cheap: drop the storage credential and external location, fix the cloud-side grant, recreate. Nothing depends on it until catalogs are built on top, which is exactly why this is done first. The one thing to avoid is deleting a cloud identity that existing external locations still reference — orphan them and every table underneath stops resolving.

## Automation opportunity

- Terraform the whole chain — cloud identity, grant, storage credential, external location — so the target is reproducible and reviewable rather than click-configured. See [Terraform patterns](/templates/terraform-patterns).
- The AWS three-pass dance is scriptable end to end: create with placeholder, create credential, read external ID, update trust policy, validate. Doing it by hand once per environment is how the placeholder gets left in place.
- Add credential validation to the post-deploy check so a broken grant fails a pipeline rather than a migration.
