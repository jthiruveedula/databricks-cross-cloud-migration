# Identity federation

Databricks accounts support SSO via SAML 2.0 and OIDC, and user/group provisioning via SCIM. Federation must be reconfigured in the target account because the cloud identity provider changes or is scoped differently.

## SSO configuration

| Source IdP | Target IdP | Notes |
|------------|------------|-------|
| Azure AD / Entra ID | Same Entra ID | Easiest if tenant is shared; otherwise reconfigure SAML app |
| AWS IAM Identity Center | Same IAM IC | Use IAM IC SCIM endpoint for the target account |
| Google Workspace | Same Workspace | Reconfigure OIDC/SAML app in target account |

<Callout client:visible variant="prerequisite" title="Account admin access">
  Configure federation as the first step in the target account. If you lock yourself out, use the Databricks account recovery process.
</Callout>

## SCIM provisioning

- Create a new Databricks account-level SCIM application in the target identity provider.
- Map groups that should be account-level groups. Do not provision workspace-local groups.
- Use nested groups carefully; not all providers flatten them the same way.

## Workspace-local to account groups

Before migrating, convert workspace-local groups to account-level groups — this ensures grants and workspace attachments work correctly. The mechanics (export, create matching account-level groups, reassign ownership/grants, retire workspace-local groups) are the same regardless of cloud change; see [UCX-assisted migration](/governance/ucx-strategy)'s group migration workflow for the actual `migrate-groups` job, or run the equivalent steps manually if not using UCX.

## Session and token invalidation at cutover

<Callout client:visible variant="warning" title="Reconfiguring SSO does not end sessions that already exist">
  [Cutover](/execution/cutover) and [network security](/security/network-security) both assume source becomes read-only at the freeze. A SAML/OIDC session established before the freeze, or a long-lived personal access token, keeps working against source until it naturally expires — reconfiguring the IdP in the target account does nothing to it. If the source IdP's session TTL is longer than your freeze window, "read-only" is a policy, not a fact, until sessions actually lapse.
</Callout>

- Note the source IdP's maximum session TTL before cutover — it's the real lower bound on how fast the freeze is enforced end-to-end, not the moment you flip write permissions.
- Where the IdP supports it, force-revoke active sessions/tokens for the source app at freeze time rather than waiting them out.
- Inventory and rotate or revoke source personal access tokens as part of the [what does not migrate](/execution/what-does-not-migrate) export — a forgotten PAT is a write path that survives the freeze.

## Validation

- Test SSO login to the target account with a non-admin user.
- Verify group membership and account-level permissions.
- Confirm service principals can authenticate with OAuth tokens.

## Rollback

If federation fails, keep a local account admin account enabled for break-glass access. Reconfigure the SAML/OIDC application and retest.

## Automation opportunity

- Use the Databricks Account SCIM API to create groups and assign users.
- Store group-to-permission mappings in a configuration file and apply them idempotently.
