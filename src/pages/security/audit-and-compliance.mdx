# Audit and compliance

A cross-cloud migration creates a discontinuity in your audit trail: source-cloud logs stop being the system of record, and target-cloud logs start — at different times, in different formats, in different tools. Compliance and audit teams need this discontinuity documented and bridged, not discovered during the next audit cycle.

<Callout client:visible variant="prerequisite" title="Loop in compliance before cutover, not after">
  If any migrated workload is in scope for SOC 2, HIPAA, PCI, or similar, involve compliance/audit stakeholders during planning — not as a post-cutover notification. Evidence-collection gaps during the transition window are hard to backfill after the fact.
</Callout>

## What changes

| Area | Source | Target |
|------|--------|--------|
| Control-plane audit logs | Cloud-native format (e.g. Azure diagnostic logs) | Different cloud-native format (e.g. CloudWatch, Cloud Logging) |
| Unity Catalog audit | System tables / account console | Same mechanism, new metastore — history does not carry over |
| Access reviews | Tied to source IAM/Entra ID groups | Tied to target IAM/service accounts — mapping must be traceable |
| Billing/cost audit | Source cloud cost export | Target cloud cost export — no unified view without extra tooling |

## Bridging the audit trail

- **Export and retain source audit logs** for the compliance-mandated retention period before decommissioning source infrastructure — don't assume the source cloud account will still exist when the next audit happens.
- **Document the cutover timestamp precisely** per workload, so auditors can identify which system of record applies to any given period.
- **Preserve the principal mapping** from [IAM mapping](/security/iam-mapping) as a durable artifact — an auditor asking "who had access to this table on this date" needs to trace through both source and target identity systems for anything spanning the cutover.

<CodeBlock client:visible language="sql" filename="export_uc_audit.sql" code={`-- Export Unity Catalog audit history before decommissioning the source metastore
SELECT event_time, event_type, user_identity, request_params, response
FROM system.access.audit
WHERE event_date >= '<CUTOVER_DATE>'
ORDER BY event_time;
`} />

## Verifying a certification actually covers the target

"Any compliance certifications scoped to the source environment have a documented transition plan" is a checkbox until it names what to actually go check. A certification is scoped to specific cloud accounts, regions, and services — moving to a new cloud, region, or Databricks deployment type does not automatically carry it over, and nobody discovers a gap here from the Databricks console.

<Callout client:visible variant="warning" title="Ask the provider, don't assume the badge transfers">
  Databricks' and each hyperscaler's own compliance attestations (SOC 2 Type II, ISO 27001, HIPAA, PCI-DSS, FedRAMP, etc.) are scoped documents — they name the specific regions, services, and deployment types in scope for a given attestation period. A certification your source deployment relied on may not list the target region or the specific compute type (serverless, in particular — see [data residency](/security/data-residency)) yet.
</Callout>

Concrete steps, not a checkbox:

1. **Pull the current scope document.** Databricks publishes its compliance attestations and their in-scope regions/services through its Trust Center / compliance portal (request through your account team if not self-serve); the target cloud provider publishes the equivalent for its own services. Read the actual scope table — don't rely on a sales deck saying "we're SOC 2 compliant."
2. **Check the target region and service by name.** A certification covering "Databricks on AWS" does not automatically mean every AWS region, or every compute type (classic vs. serverless), is in scope for that attestation period — confirm the specific region and service the migration lands on appears in the current scope document.
3. **Get it in writing, dated.** An email or portal confirmation naming the target region/service and the attestation period it's covered under is the artifact an auditor will ask for — a verbal assurance from an account manager is not.
4. **Re-check on renewal, not just at migration time.** Attestation scope can change between audit cycles. A certification that covered the target region at migration time is not guaranteed to still cover it a year later — put a recheck on the same cadence as the certification's renewal.

## Auditing across the dual-run window, not just the cutover moment

The "different systems at different times" framing above assumes a clean instant of cutover. It isn't one: [metastore migration](/governance/metastore-migration)'s bulk-clone-then-freeze pattern and [network security](/security/network-security)'s "keep both networks live through hypercare" guidance both describe source and target running concurrently for days to weeks, not a single moment. That overlap needs its own answer, not an extension of the pre/post framing.

<Callout client:visible variant="decision" title="Name the system of record for every timestamp in the overlap, before it starts">
  For the duration of dual-run, decide and document: which system is authoritative for which workload, at which point — not "whichever one an auditor asks about first." A workload cut over on day 3 of an 11-day dual-run has target as system-of-record from day 3 onward even though source is still live and still being read; a workload still on source until day 9 has source as system-of-record until then. Write this table down per workload before dual-run starts, not reconstructed from memory when an auditor asks.
</Callout>

- **Log both sides for the full overlap**, not just the side currently designated system-of-record — a question about day 5 needs day-5 logs from whichever side actually served the request, and during dual-run either side legitimately might have.
- **Capture the per-workload cutover timestamp**, not just one migration-wide cutover date — see the table above. This is what lets an auditor map "requests against this workload on this date" to the correct log source without a project-wide timeline as the only reference.

## Compliance sign-off checklist

Before hypercare exit, confirm with compliance/security stakeholders:

- Source audit logs are exported and archived per retention policy.
- Target audit logging (Unity Catalog system tables, cloud-native control-plane logs) is enabled and verified from day one of the target workspace — not enabled retroactively after go-live.
- Access review processes have been updated to reference the target identity system.
- Any compliance certifications scoped to the source environment have a documented transition plan to the target.

<Callout client:visible variant="decision" title="Don't decommission source logs on the same timeline as source compute">
  Compute and storage decommission (see [hypercare](/execution/hypercare)) typically happens faster than audit-log retention requirements allow. Export and archive logs independently of infrastructure decommission — the log retention clock rarely matches the infrastructure teardown clock.
</Callout>

## Validation

- Have compliance stakeholders formally sign off that audit continuity is documented before source decommission — see [business validation](/validation/business-validation).
- Spot-check that target audit logging actually captured events during the pilot wave; a misconfigured audit pipeline that silently drops events is worse than no migration at all from a compliance standpoint.

## Rollback

Audit and compliance concerns don't block a technical rollback, but any rollback event itself must be logged and retained with the same rigor as the migration — an unexplained gap where source was briefly re-enabled is exactly the kind of thing an audit will flag.

## Automation opportunity

- Automate source audit log export as a scheduled job with a defined retention target, rather than a manual one-time export before decommission.
- Build a single query/dashboard that spans both source-export and target-native audit logs for any workload that crossed the cutover boundary, so auditors don't need to manually stitch two systems together.
