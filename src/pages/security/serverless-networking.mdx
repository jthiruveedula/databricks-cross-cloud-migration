# Serverless networking and egress

[Network security](/security/network-security) covers the classic compute plane — the VNet, VPC, or subnet your clusters run in. Serverless compute does not run there. It runs in a Databricks-managed network, and every control you built for the classic plane has a different name, a different scope, and a different owner.

This matters more on a cross-cloud move than it looks, for a reason nobody plans for: **serverless is on by default in new workspaces.** A target workspace stood up in 2026 will happily run SQL warehouses, jobs, and pipelines on serverless compute while the migration team is still building the VNet they assumed everything would use.

## The one-paragraph version

Serverless egress is governed by a **network connectivity configuration (NCC)** — an *account-level, regional* object created by an account admin and attached to one or more workspaces in that region. Every private endpoint rule on the NCC applies to every workspace attached to it. That is three properties your classic networking does not have: account-level, regional, and shared.

<Callout client:visible variant="warning" title="Account-level and regional means it is not the workspace team's to create">
  A platform engineer with workspace admin cannot create an NCC. It needs an **account admin**, and one NCC serves every attached workspace in the region — so its rules are a shared blast radius. On a migration this is a scheduling dependency, not a technical one: if your account admin is a different team in a different timezone, put the NCC request in during discovery, not the week of cutover.
</Callout>

## What differs from the classic plane

| | Classic compute | Serverless compute |
|---|---|---|
| Runs in | Your VNet / VPC | Databricks-managed network |
| Egress controlled by | Your route tables, NAT, firewall | **NCC** + network policies |
| Private connectivity via | VNet injection, PrivateLink, PSC | **NCC private endpoint rules** |
| Scope of the control | Per workspace | **Per NCC, shared by attached workspaces** |
| Created by | Cloud/network team | **Account admin** |
| Source IPs seen by your firewall | Your NAT gateway | **NCC stable IPs** |

<Callout client:visible variant="warning" title="If you copied stable IPs from the NCC UI before mid-2026, that list is already gone">
  Databricks decommissioned the legacy Public Preview stable-IP list on **25 May 2026**; after that date it is no longer available through the NCC UI or the Network Connectivity API, and any allow-list still built from it is stale. Re-derive the IP ranges from the current method rather than from a runbook, a wiki page, or a firewall rule someone wrote in 2025 — and check the firewall rules you are *migrating*, since a copied allow-list carries the stale values into the target. See the [serverless networking documentation](https://docs.databricks.com/aws/en/security/network/serverless-network-security/) for the current source of truth.
</Callout>

## Where this bites on a migration, specifically

| Symptom | Cause |
|---|---|
| Serverless SQL warehouse cannot read target storage; classic clusters can | Storage firewall allows the VNet/VPC but not the NCC stable IPs |
| Works in target region A, fails in region B | Two NCCs, rules added to one |
| Job hangs rather than fails | Egress silently blackholed rather than refused |
| Worked in the pilot, fails at scale | Pilot ran on classic compute; production defaults to serverless |
| Partner integration stops after cutover | Their allow-list still holds the source cloud's NAT IPs |

<Callout client:visible variant="tip" title="Test with serverless explicitly during the pilot">
  A pilot that runs everything on a classic cluster proves nothing about serverless egress. Run at least one job and one SQL warehouse query on serverless compute against target storage during the [pilot](/execution/pilot), while there is still time for an account admin to add a rule.
</Callout>

## Validation

- Every target region has an NCC, attached to every workspace in that region, and the NCC id is recorded against each workspace in the inventory.
- A serverless SQL warehouse query and a serverless job both succeed against target storage, from each target region.
- Every firewall that filters by source IP has been updated with the current NCC stable IPs — re-derived, not copied from a pre-mid-2026 list.
- Private endpoint rules exist and are **approved** on the resource side for every private destination.
- The classic-plane and serverless-plane controls have been reviewed together, so a destination reachable by one and not the other is a deliberate choice.

## Rollback

Networking changes are configuration and are reversible, with one caveat worth stating: removing a private endpoint rule or an NCC affects **every workspace attached to that NCC**, not just the one you were working on. Before changing a shared NCC during hypercare, check what else is attached.

## Automation opportunity

- Record the NCC id as a workspace attribute in the [workspace inventory](/discovery/workspace-inventory), so "which workspaces share egress rules" is a query rather than an investigation.
- Add a serverless smoke test to the post-cutover validation job — one serverless query against target storage per region — rather than relying on classic-compute tests to cover it.
- Treat firewall allow-lists as code. A stable-IP list that lives in a wiki is the one that goes stale.
