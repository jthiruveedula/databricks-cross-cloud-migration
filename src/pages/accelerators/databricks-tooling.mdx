# Databricks migration tooling

A cross-cloud migration is a platform-modernization program with a data workstream attached. The tooling below is the accelerator layer that keeps the data workstream from dominating the timeline.

<ArchifyDiagram client:visible name="databricks-tooling.architecture" type="architecture" title="The accelerator stack" caption="Every tool automates the mechanical parts and hands the judgment calls — compute re-mapping, logic equivalence — to a human." />

## The accelerator map

Do not write what Databricks already maintains. Almost every mechanical layer of a cross-cloud move has a field-maintained accelerator behind it; the work that remains is scoping them, sequencing them, and owning the objects none of them cover.

| Tool | Owner | Automates | Stops at |
| --- | --- | --- | --- |
| **UCX** | Databricks Labs (OSS) | Assessment, group + table upgrade to Unity Catalog | Cross-cloud data move; notebook rewrite partial |
| **Lakebridge** | Databricks (free, GA) | DW/ETL conversion + reconciliation | Legacy orchestration mapping |
| **[databricks-replicator](https://github.com/databricks-solutions/databricks-replicator)** | Databricks Solutions | Cloud-agnostic UC metadata + data replication across metastores | UC functions and models (in development); ownership; row filters and column masks; Hive |
| **[workspace-migration](https://github.com/databricks-solutions/workspace-migration)** | Databricks Solutions | UC objects a replicator skips — functions, models, filters/masks/ABAC, connections, Delta Sharing — plus legacy Hive, as a deployable bundle | Its stated scope is control-plane/region moves, not cross-cloud; materialized views and streaming tables hard-skipped |
| **[ai-platform-kit](https://github.com/databricks-solutions/ai-platform-kit)** | Databricks Solutions | Standing up the *target*: workspace, Unity Catalog, identity, private networking on Azure, AWS and GCP | Not a certified landing zone — it writes Terraform you review |
| **[flowx](https://github.com/databricks-solutions/flowx)** | Databricks Solutions | Azure Data Factory and Airflow pipelines into Lakeflow Jobs, packaged as bundles | Source-system connectivity and credentials |
| **[Power BI migration accelerator](https://github.com/databricks-solutions/powerbi-on-databricks-migration-accelerator)** | Databricks Solutions | Bulk repointing of `.pbip` semantic models at Databricks SQL + UC | Converting reports to Metric Views or AI/BI dashboards |
| **[alteryx-to-databricks-converter](https://github.com/databricks-solutions/alteryx-to-databricks-converter)** | Databricks Solutions | `.yxmd` workflows into PySpark, DLT, Spark SQL, Lakeflow Designer | Unsupported tools are reported, not guessed |
| **[databricks-waf](https://github.com/databricks-solutions/databricks-waf)** | Databricks Solutions | Post-migration Well-Architected assessment traced to evidence | Alpha; it reviews the target, it never migrates |
| **[mlflow-export-import](https://github.com/mlflow/mlflow-export-import)** | MLflow (OSS, Apache-2.0) | Bulk MLflow experiment/run/model export-import, incl. cross-metastore UC model copy | Custom artifact locations; Databricks notebook-revision linking |
| **databrickslabs/migrate** | Databricks Labs (OSS) | Workspace-to-workspace asset export/import | Compute re-map across clouds |
| **Asset Bundles / Terraform** | Databricks | IaC replicas of jobs, pipelines, notebooks | Runtime differences across clouds |

<Callout variant="warning" title="Read each tool's own coverage table before you plan around it">
The "stops at" column above is each project's own statement, not an estimate. Two of them matter more than the rest: **no** accelerator migrates a materialized view or a streaming table — both skip them, and the object is rebuilt by refreshing its pipeline against the target at cutover — and **workspace-migration does not claim cross-cloud** in its README (its stated cases are control-plane migrations, account consolidations, and cross-region moves). Validate its data path on a pilot catalog before relying on it across clouds, and use the replicator for the cross-cloud table move either way.
</Callout>

## UCX — assessment and Unity Catalog upgrade

UCX (Unity Catalog Migration Assistant) is an open-source Databricks Labs project. Install it via the Databricks CLI. It is **not SLA-supported** — treat it as a power tool, not a managed service.

Two workflows matter most:

1. **Assessment** crawls tables, UDFs, grants, mounts, jobs, clusters, DLT, and init scripts, then produces a Migration Assessment Report + dashboards that flag every incompatibility *before* you change anything.
2. **Group + table migration** upgrades workspace-local groups to account-level groups, replicates permissions, and moves Hive Metastore tables/views to Unity Catalog — migrating storage credentials and external locations automatically.

<Callout variant="warning" title="UCX is a UC upgrade tool, not a cross-cloud mover">
UCX enables each side for Unity Catalog. The actual cross-cloud data move is done by standing up a separate target workspace + metastore and moving data via Delta Sharing, Deep Clone, or D2D replication. UCX also explicitly flags that **cross-cloud external locations are not supported** — use Delta Sharing for cross-cloud mounts.
</Callout>

<CodeBlock
  language="bash"
  code={`# Install and run the UCX assessment
databricks labs install ucx
databricks labs ucx assessment --workspace <source-workspace-url>

# Review the produced report, then upgrade groups + tables
databricks labs ucx migrate-groups --workspace <source-workspace-url>
databricks labs ucx migrate-tables  --workspace <source-workspace-url>`}
/>

Known limits: notebook/function auto-rewrite is still under development (not GA as of 2026-06); legacy TABLE ACL (DENY semantics) cannot auto-map to UC's model and needs grant redesign; DBFS-root managed tables cannot be governed by UC and must be Deep Cloned to cloud storage first.

## Lakebridge — data warehouse and ETL conversion

Lakebridge is Databricks' free, open migration engine (GA). It automates **up to 80% of a warehouse migration** and is growing ~20% month-over-month across 1,000+ customers/partners.

Three components:
- **Analyzer** — profiles and assesses source schemas (Teradata, Synapse, and more).
- **Converter** — rule-based + AI-powered conversion of SQL/ETL to Databricks SQL / Spark SQL.
- **Validator** — schema-, row-, and column-level reconciliation against the source.

<Callout variant="tip" title="Pair Lakebridge with AI-assisted translation">
Lakebridge's deterministic converter is the "core" in the hybrid pattern. Where it cannot express a transform, the AI-powered converter and the [AI-assisted migration](/accelerators/ai-assisted-migration) playbook take the edge cases — always gated by the Validator.
</Callout>

## ai-platform-kit — standing up the target first

Nothing else on this page has anywhere to land until the target platform exists. [`databricks-solutions/ai-platform-kit`](https://github.com/databricks-solutions/ai-platform-kit) is the accelerator for that half: workspace provisioning with VNet/VPC injection and secure cluster connectivity, an opinionated Unity Catalog setup (self-managed metastore, per-env catalogs, external locations, medallion schemas), account-level SCIM groups and tiered RBAC, SQL warehouses, cluster policies, secret scopes, IP access lists, and private connectivity — Private Link on AWS, Private Endpoints on Azure, Private Service Connect on GCP, plus NCC for serverless egress.

It ships as agent skills rather than templates: the agent writes Terraform and SDK calls against your stated requirements, then runs a three-path verification (classic cluster, serverless SQL warehouse, serverless notebook job) designed to catch the configuration failures that otherwise surface a week later. It brings no credentials of its own — you authenticate `az`/`aws`/`gcloud` and the Databricks CLI yourself.

<Callout variant="warning" title="Generated Terraform is a draft, not a landing zone">
The kit is explicit that it ships skills and glue, not a certified reference architecture. Review every generated Terraform plan against your own network and security standards — the [network security](/security/network-security) and [identity federation](/security/identity-federation) pages are the checklist to review it against — and keep the state file under the same controls as any other production IaC.
</Callout>

## databricks-replicator — the cross-cloud data path

[`databricks-solutions/databricks-replicator`](https://github.com/databricks-solutions/databricks-replicator) is the one accelerator here that states cloud-agnostic, cross-metastore replication as its purpose, which makes it the default mover for the table workstream. It performs incremental metadata + data replication via D2D Delta Sharing, Deep Clone and Auto Loader, handles the streaming-table backing-table complexity (it clones the backing table, not the streaming table), and reconciles row counts and schema after every run.

Its own coverage table is the thing to plan against. Supported: storage credentials, external locations, tag policies, catalogs, schemas, volumes, tables, views, comments, SQL-defined materialized views and streaming tables, tags, and per-securable grants. **Not** replicated: object ownership, row filters and column masks, Hive metastore, and workspace assets — with UC functions and registered models still listed as in development.

Configuration is YAML with Pydantic validation, so scope (catalogs, schemas, tables), storage-URL rewrites (`cloud_url_mapping`) and principal translation (`principal_mapping`) are all declarative — which is exactly why they can be generated rather than typed (see [one config, every accelerator](#one-config-every-accelerator) below).

## workspace-migration — the UC objects a replicator leaves behind

[`databricks-solutions/workspace-migration`](https://github.com/databricks-solutions/workspace-migration) is a Databricks Asset Bundle that migrates Unity Catalog and legacy Hive Metastore objects between workspaces. It covers the long tail the replicator does not: SQL and Python functions, registered models (metadata, version artifacts and aliases), tags, row filters, column masks and ABAC policies, Lakehouse monitors, connections and foreign catalogs, and Delta Sharing shares/recipients/providers. A separate `migrate_hive` job moves legacy Hive databases, tables, views, functions and grants like-for-like into the target's own `hive_metastore` — a copy, not a Unity Catalog upgrade, so UCX still owns that step.

Deploy-time it needs a service principal with workspace admin on both sides, metastore-level `CREATE_*` privileges, and `USE_PROVIDER` on the target. Scope comes from `catalog_filter`/`schema_filter`; progress and pre-check results land in tracking tables plus a bundled dashboard.

Two limits decide how you sequence it. Materialized views and streaming tables are hard-skipped (`skipped_by_stateful_service_migration`) — schema and grants migrate, the object is rebuilt by a pipeline refresh at cutover. DLT pipelines, model serving endpoints and Apps go through the Terraform exporter instead. And, as the callout above says, its README frames it as a control-plane/account/region tool — treat cross-cloud use as something you prove on a pilot catalog.

## flowx — external orchestrators into Lakeflow Jobs

[`databricks-solutions/flowx`](https://github.com/databricks-solutions/flowx) converts Azure Data Factory and Apache Airflow pipelines into Databricks Lakeflow Jobs packaged as bundles, in three phases: discover (ARM/JSON parse for ADF, static AST parse for Airflow), convert (deterministic mappings for known activity/operator types, LLM-assisted for the rare ones), and package (bundle YAML, notebooks, setup scripts). Both sources emit the same intermediate representation, so only discovery and translation are source-specific.

This is the accelerator for the [external orchestrators](/pipelines/external-orchestrators) decision: where that page says a cross-cloud move is the moment to ask whether the external orchestrator should survive at all, flowx is what makes "fold it into Lakeflow" a scoped conversion rather than a rewrite. Deterministic coverage is published per activity type — check your inventory against it before committing a date, and treat every agentically-translated activity as needing review.

## Power BI and Alteryx — the last mile off the source stack

Two accelerators handle the analytics-side work that a metastore migration leaves untouched:

- [`powerbi-on-databricks-migration-accelerator`](https://github.com/databricks-solutions/powerbi-on-databricks-migration-accelerator) bulk-repoints `.pbip` semantic models at Databricks SQL + Unity Catalog by rewriting Power Query M from a single validated JSON configuration, with `-WhatIf` previews, optional dataset backups and a test suite gating each change. It repoints connections; it does **not** convert reports into Metric Views or AI/BI dashboards. See [BI tool reconnection](/analytics/bi-tool-reconnection).
- [`alteryx-to-databricks-converter`](https://github.com/databricks-solutions/alteryx-to-databricks-converter) turns `.yxmd` workflows into PySpark, DLT, Spark SQL and Lakeflow Designer output in one run, with no Alteryx licence required. Unsupported tools are reported rather than silently dropped — the report is the manual-work list.

## databricks-waf — proving the target after the move

[`databricks-solutions/databricks-waf`](https://github.com/databricks-solutions/databricks-waf) assesses a workspace or account against the seven pillars of the Databricks Well-Architected Framework and keeps the chain from requirement to evidence to affected resource to action to later verification intact. Run it against the target during [hypercare](/execution/hypercare), not during cutover: it is the structured version of "is the new platform actually built well", and its published reports are the artifact for [business validation](/validation/business-validation) sign-off. It is alpha — treat its output as an input to review, not a certificate.

## One config, every accelerator

Each accelerator has its own config file, and each one wants the same three facts: which catalogs are in scope, which storage prefix becomes which, and which source principal becomes which target principal. Typing those three times is how a migration ends up mis-scoped in exactly one tool — and a mis-scoped filter is a silent partial migration, not an error.

The runbook's companion toolkit emits them instead. `dbxmig handoff` reads the migration config and the source inventory the rest of the toolkit already uses and writes a ready-to-run `config.yaml` for workspace-migration, an `environments.yaml` plus one replication-group config per catalog for databricks-replicator, and a `HANDOFF.md` routing note that names which accelerator owns which object class — and lists the objects, in your inventory, that **none** of them move.

<CodeBlock
  language="bash"
  code={`dbxmig -c migration.yaml handoff -i inventory.json -o ./handoff

# handoff/
#   workspace-migration/config.yaml          catalog_filter, dry_run: true, on_target_collision: fail
#   databricks-replicator/environments.yaml  source + target workspace hosts
#   databricks-replicator/<cat>_to_<cat>.yaml  cloud_url_mapping + principal_mapping from path_rules
#   HANDOFF.md                                who moves what, and what nothing moves

# Exits non-zero when something needs a decision -- an object no accelerator
# covers, or a storage location with no path rule -- so it gates CI.`}
/>

<Callout variant="tip" title="The emitted configs start in dry-run on purpose">
The workspace-migration config is written with `dry_run: true` and `on_target_collision: fail`, and every replicator group has reconciliation enabled. The first run of an accelerator against a target metastore should produce a report, not a write — the same reason [`dbxmig apply`](/templates/automation-toolkit) is dry-run unless you pass `--execute`.
</Callout>

## mlflow-export-import — ML tracking and registry, cross-account

None of the accelerators above touch MLflow — experiments, runs, and registered models are workspace-local state with no UC equivalent to replicate. [`mlflow/mlflow-export-import`](https://github.com/mlflow/mlflow-export-import) (maintained under the official MLflow GitHub org, Apache-2.0) is the bulk export/import tool for that gap: `export-all`/`import-all` moves every object type (runs, experiments, registered models, logged models, traces, prompts, evaluation datasets) through an intermediate directory, so source and target never need to reach each other directly. Its `copy-model-version` CLI additionally does what the raw MLflow client cannot — copy a model version across two different UC metastores in different accounts, via two Databricks CLI profiles.

It already avoids the two failure modes a hand-rolled migration script tends to hit silently: it pages `search_runs` instead of trusting a single 1000-row page, and it replays full metric history instead of only the latest value per key. See [MLflow](/ml/mlflow) and [model registry](/ml/model-registry) for the exact commands and what still needs a hand-rolled fix afterward (custom artifact locations, Databricks notebook-revision links).

## migrate — workspace asset export/import

`databrickslabs/migrate` does workspace-to-workspace cross-cloud export/import with checkpointing and validation. Good for moving notebooks, jobs, and configuration. Caveat: classic compute differs across clouds, so clusters and jobs usually need a manual re-map even after import.

## Asset Bundles and Terraform — repeatable provisioning

Databricks Asset Bundles (declarative automation, YAML) let you express jobs, pipelines, dashboards, and models as versioned infrastructure. The Terraform Exporter recreates a workspace as code for repeatable target provisioning and compliance review.

<CodeBlock
  language="yaml"
  code={`# databricks.yml — a bundle that provisions migration target resources
bundle:
  name: cross-cloud-migration-target

resources:
  jobs:
    ingest_raw:
      name: "Ingest (Auto Loader)"
      tasks:
        - task_key: load
          notebook_task:
            notebook_path: ../notebooks/load_raw
  pipelines:
    dlt_medallion:
      name: "Medallion (DLT)"
      catalog: target_catalog
      target: prod`}
/>

## How the tools compose in a real program

<CodeBlock
  language="text"
  code={`discovery   -> UCX assessment + dbxmig inventory/gaps (readiness, incompatibilities)
foundation  -> ai-platform-kit (target workspace, UC, identity, networking)
            -> dbxmig handoff (one scope, emitted into every accelerator's config)
data move   -> databricks-replicator (Deep Clone / D2D Delta Share, incremental)
            -> workspace-migration (functions, models, filters/masks, connections)
            -> Lakebridge converter where the source is a foreign warehouse
pipelines   -> flowx (ADF/Airflow -> Lakeflow Jobs), dbxmig bundle (jobs, paused)
            -> Terraform exporter (DLT, model serving, Apps)
analytics   -> Power BI accelerator (repoint), alteryx2databricks (convert)
rebuild     -> materialized views + streaming tables: refresh the pipeline. No
               accelerator moves these.
validate    -> Lakebridge Validator, dbxmig reconcile, databricks-waf assessment
cutover     -> Replicator keeps the target warm; UCX shadow tables for rollback`}
/>
