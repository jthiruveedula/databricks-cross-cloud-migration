# Cutover

Cutover is the moment the target environment becomes the system of record. It requires a freeze window, final data catch-up, job re-enablement, and user redirection.

## Cutover prerequisites

<Callout client:visible variant="prerequisite" title="Go/no-go gate">
  Do not proceed with cutover until every domain below has an explicit, named sign-off. Hold a formal go/no-go call and record the decision — "everyone was busy so we assumed it was fine" is not a sign-off.
</Callout>

<Checklist client:visible title="Go/no-go gate — one sign-off per domain" items={[
  { id: 'technical', label: 'Technical: target infrastructure provisioned and passes technical validation' },
  { id: 'data', label: 'Data: reconciliation shows exact parity per data-reconciliation\'s dimensions (0% variance, not a negotiated tolerance)' },
  { id: 'security', label: 'Security: identity, groups, secrets, and network validation passed' },
  { id: 'business', label: 'Business: stakeholders have signed off per business validation' },
  { id: 'operational', label: 'Operational: support roster, rollback plan, and hypercare severity matrix are in place' },
  { id: 'cost', label: 'Cost: double-running spend is within the modelled multiple, or the variance is approved by whoever owns the budget — see cost and tagging continuity' },
  { id: 'communication', label: 'Communication: cutover window and contact channel sent to affected users' },
  { id: 'preservation', label: 'Preservation: everything on what does not migrate is exported and read back from the target' },
]} />

If any domain is not signed off, the answer is no-go — reschedule rather than proceed on a partial gate.

<Callout client:visible variant="warning" title="The preservation gate is the only one with no rollback">
  Audit history, job run history, workspace object ACLs, and notebook revisions are destroyed by the move rather than migrated by it, and none of it is recoverable once the source is gone. Everything else on this gate can be fixed forward after cutover — see [what does not migrate](/execution/what-does-not-migrate).
</Callout>

## Cutover sequence

<CutoverSwimlane />

| Step | Action | Owner |
|------|--------|-------|
| 1 | Announce maintenance window | Migration PMO |
| 2 | Pause source jobs and writes | Platform team |
| 3 | Drain: confirm zero active runs on source | Platform team |
| 4 | Final incremental sync | Data team |
| 5 | Run final reconciliation | QA / data team |
| 6 | Switch DNS/endpoints/connection strings | Network team |
| 7 | Enable target jobs in dependency order | Platform team |
| 8 | Verify first target runs | Application teams |
| 9 | Open support channel | Migration PMO |

<Callout client:visible variant="warning" title="Pausing a job disables future triggers — it does not stop a run already in flight">
  Step 2 stops new runs from being scheduled; it does nothing to a job that started five minutes before the freeze. Proceeding straight to final sync while a source job is still writing is the exact split-brain precondition [rollback](/execution/rollback) exists to prevent — the sync captures a state the source is still mutating underneath it. Poll the Jobs API's `active_only=true` filter on `List job runs` (active states: `QUEUED`, `PENDING`, `RUNNING`, `TERMINATING`) after step 2, and do not proceed to step 4 until it returns zero across every source job — or the drain hits a hard timeout, in which case treat it as a no-go, not a "close enough." `dbxmig cutover-drain --side source` runs exactly this poll-with-timeout loop against a live workspace instead of leaving it to a person watching a dashboard.
</Callout>

## Final sync and read-only mode

Set source tables to read-only if possible:

<CodeBlock client:visible language="sql" code={`-- Example: revoke write privileges on source catalog during freeze
REVOKE ALL PRIVILEGES ON CATALOG source_catalog FROM \`users\`;
GRANT SELECT ON CATALOG source_catalog TO \`users\`;`} />

Run final catch-up based on table type:

- **Delta tables:** Apply incremental `DEEP CLONE` or merge changes.
- **Streaming:** Restart from last checkpoint offset.
- **Volumes:** Sync any files changed since last run.

## Cloud-specific caveats

DNS/endpoint switch mechanics in Step 5 are not interchangeable across clouds: Azure Traffic Manager/Front Door, AWS Route 53, and GCP Cloud DNS have different propagation timing and health-check semantics. Rehearse the actual cutover DNS/endpoint change against the target cloud's tooling during the [pilot](/execution/pilot), not for the first time on cutover night.

## Validation

- Re-run row-count and checksum queries.
- Start a sample job from each critical pipeline.
- Verify user login, SSO, and permissions.

## Rollback

If cutover fails:

1. Stop target writes and jobs.
2. Re-enable source jobs from the last consistent state.
3. Redirect users and applications back to source.
4. Investigate and schedule a new cutover window.

## Automation opportunity

- `dbxmig cutover-drain` runs step 3's poll for you: it checks `active_only=true` on the named workspace on an interval and exits non-zero on a hard timeout instead of a silent "close enough" — see the [automation toolkit](/templates/automation-toolkit). It is read-only: it answers "is it safe to proceed," it does not pause jobs (step 2) or run the sync (step 4) itself.
- Step 2 (pausing jobs) and step 4 (final sync) are still manual or bundle-specific — [Asset Bundles](/pipelines/cicd-promotion) can set a job's schedule to `PAUSED` at deploy time, but that's a static flag, not an orchestrated pause across every job on the workspace.
- Integrate with orchestration tools for dependency-aware job startup.
