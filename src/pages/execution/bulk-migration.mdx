# Bulk migration

Bulk migration is the pilot's runbook, repeated across every remaining wave from [wave planning](/execution/wave-planning) — at scale, on a schedule, with the same reconciliation rigor. The goal at this stage is throughput and consistency, not discovery; anything still being discovered here should have surfaced during the [pilot](/execution/pilot). If the pilot ran through the real accelerators (it should have — see [pilot](/execution/pilot)), bulk migration is running the same accelerators again, wave by wave, not writing new migration code.

<Callout client:visible variant="prerequisite" title="Don't start bulk migration on an unvalidated runbook">
  If the pilot retro found gaps in tooling, IAM mapping, or reconciliation, close them before wave 1 — bulk migration multiplies whatever is broken in the runbook across every remaining workload.
</Callout>

## The default: run the accelerators per wave, not a script per table

<Callout client:visible variant="tip" title="dbxmig handoff -> databricks-replicator / workspace-migration, one config per wave">
  Each wave is a set of catalogs and jobs, not an ad-hoc table list — so each wave gets its own accelerator run, driven by `dbxmig handoff`'s output rather than a wave-specific script:

  <CodeBlock client:visible language="bash" filename="run_wave.sh" code={`# Scope this wave's inventory (catalogs/schemas the wave plan assigned here),
# then emit the accelerator configs for exactly that scope -- see the
# automation toolkit and dbxmig handoff.
dbxmig -c migration.yaml handoff -i wave-2-inventory.json -o ./wave-2-handoff

# databricks-replicator does the table/volume/metadata move for this wave's
# catalogs. Concurrency is a WITHIN-catalog knob (concurrency.max_workers,
# 1-64, default 8) -- catalogs in a wave still process one at a time, so
# throughput comes from raising max_workers, not from adding catalogs.
data-replicator wave-2-handoff/databricks-replicator/*.yaml \\
  --target-catalogs "$(cat wave-2-target-catalogs.txt)"

# workspace-migration picks up what the replicator doesn't: functions,
# models, row filters/column masks, connections. Runs as its own DAB job.
databricks bundle deploy --var migration_spn_id=<app-id> -t wave-2

# Jobs for this wave: the Terraform Exporter or a scripted bundle-init loop
# (see workflows and jobs), scoped to this wave's job-ownership tags.`} />

  This is the same sequence the pilot ran, at wave scale — see [pipelines and workflows](/pipelines/workflows-jobs) for the job-side detail and [Databricks migration tooling](/accelerators/databricks-tooling) for what each accelerator does and does not cover.
</Callout>

<Callout client:visible variant="warning" title="Parallelism has a real ceiling, and it's per-catalog, not per-wave">
  databricks-replicator's own validated range for `concurrency.max_workers` is 1-64 (default 8) — and catalogs process **strictly sequentially**, confirmed from the tool's own source, not its README. A wave with 6 catalogs does not get 6x throughput by adding catalogs; it gets throughput from raising `max_workers` within whichever catalog is currently running, up to that ceiling. Size wave scope (catalogs per wave, not just tables per wave) with this in mind — see the [scale-aware timeline estimator](/tools/timeline-estimator) for how catalog count and worker concurrency actually compose into a wall-clock estimate.
</Callout>

<Callout client:visible variant="tip" title="Incremental re-runs are the mechanism, not a special mode">
  Re-running the same accelerator config against an already-migrated catalog is not a fresh full copy — `databricks-replicator` reissues `CREATE OR REPLACE TABLE ... DEEP CLONE` per table, and `DEEP CLONE` only moves files that changed since the last clone. For a table still being written to during a wave's migration window, this is what lets an early clone run days before cutover and a final incremental clone run immediately before it, catching every version committed in between — the accelerator's normal behavior does this for you; it's not something the wave manifest needs to special-case.
</Callout>

## Fallback: an object type no accelerator covers

The accelerators above don't move everything — materialized views, streaming tables, and anything outside Unity Catalog need a different mechanism (see the [accelerator map](/accelerators/databricks-tooling) for exactly what's out of scope). For that residual, a hand-rolled parallel copy is still sometimes the right tool — just don't reach for it as the default:

<CodeBlock client:visible language="python" filename="bulk_migrate_fallback.py" code={`from concurrent.futures import ThreadPoolExecutor, as_completed

def migrate_table(table_name: str) -> dict:
    deep_clone(source=f"source_catalog.{table_name}", target=f"target_catalog.{table_name}")
    return reconcile(table_name)

tables = load_wave_manifest("wave-1.yaml")["tables"]
results = {}
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(migrate_table, t): t for t in tables}
    for future in as_completed(futures):
        table = futures[future]
        results[table] = future.result()

failed = [t for t, r in results.items() if not r["reconciled"]]
if failed:
    raise RuntimeError(f"Reconciliation failed for: {failed}")
`} />

<Callout client:visible variant="warning" title="Same ceiling applies here, by hand">
  Cloud storage APIs and Unity Catalog metastore operations both rate-limit. Tune `max_workers` against your source and target cloud's actual throttling limits — a naive "migrate everything at once" run degrades into throttling errors, not faster migration. This is the same constraint databricks-replicator's own `max_workers` config manages for you above; the fallback script has to manage it by hand.
</Callout>

## Per-wave sequence

| Step | Action |
|------|--------|
| 1 | Confirm previous wave's exit criteria are met |
| 2 | Freeze wave scope (no new tables/jobs added mid-wave) |
| 3 | Run `dbxmig handoff` for this wave's inventory, then the accelerators it emits configs for |
| 4 | Reconcile every table/job — Lakebridge Reconcile plus `dbxmig reconcile --live`, per [data reconciliation](/validation/data-reconciliation) |
| 5 | Re-create jobs/pipelines via the Terraform Exporter or bundle-init, per [workflows and jobs](/pipelines/workflows-jobs) |
| 6 | Grant access via Unity Catalog; verify with the owning team |
| 7 | Hold wave sign-off before starting the next wave |

## Tracking progress

Maintain a single source of truth for wave status — a stalled or partially-migrated wave is easy to lose track of across dozens of tables and jobs:

| Wave | Tables | Jobs | Status | Blocked by |
|------|--------|------|--------|-------------|
| Wave 1 | 42/42 | 8/8 | Reconciled | — |
| Wave 2 | 31/56 | 3/12 | In progress | Streaming checkpoint migration |
| Wave 3 | 0/18 | 0/9 | Not started | Wave 2 exit criteria |

## Validation

- Apply the pilot's reconciliation harness to every table and job — no wave exits on a manual spot-check alone. See [data reconciliation](/validation/data-reconciliation) for the Lakebridge Reconcile / `dbxmig reconcile` split.
- Track failure patterns across waves; a recurring failure type (e.g. a specific data type or partition scheme) means fixing the tooling, not re-running the same fix per table.
- Confirm each wave's owning team explicitly signs off before starting the next wave.

## Rollback

Roll back at wave granularity, not migration-wide — see [rollback](/execution/rollback). A failed wave 3 does not require reverting waves 1-2; keep completed waves on target and only revert the wave in question.

## Automation opportunity

- Generate wave manifests directly from the [dependency mapping](/discovery/dependency-mapping) output and `dbxmig wave-plan` (see [wave planning](/execution/wave-planning)) rather than hand-curating table lists.
- Build a dashboard from the wave-tracking table above so stakeholders can self-serve status instead of asking in standup.
