# Workflows and jobs

Databricks Workflows is the native orchestrator for notebooks, Python, SQL, and DLT tasks. Migrating jobs requires recreating definitions in the target workspace and rewriting any cloud-specific references.

## Job components to migrate

| Component | Consideration |
|-----------|---------------|
| Task graph | Export JSON and recreate; validate dependencies |
| Cluster / job cluster | Map node types, runtime, access mode |
| Notebook tasks | Ensure notebooks exist in target workspace or repos |
| Python wheel tasks | Rebuild and publish wheels to target artifact store |
| SQL tasks | Rewrite warehouse endpoint and catalog references |
| DLT tasks | Recreate pipeline in target and update catalog paths |
| Triggers | Reconfigure schedule, file arrival, or continuous triggers |
| Notifications | Update email lists and webhook endpoints |
| Permissions | Replay job ACLs with mapped principals |

## Export and import

<CodeBlock client:visible language="bash" code={`# Export all jobs from source workspace.
# List endpoints paginate -- always check the count against the workspace UI
# before trusting the export, or you migrate a page and report success.
databricks jobs list -o json > jobs-raw.json
jq 'if type=="array" then . else .jobs end | length' jobs-raw.json

jq 'if type=="array" then . else .jobs end | .[] | {job_id, settings}' \\
  jobs-raw.json > jobs.json

# Create a job in the target workspace after editing the JSON.
# The flag is --json with an @path, not --json-file.
databricks jobs create --json @job-target.json`} />

<Callout client:visible variant="warning" title="Strip the server-owned fields before re-creating, or the create fails">
  A job exported from source carries `job_id`, `created_time`, and `creator_user_name`. Those belong to the source workspace: the target assigns its own. Post the `settings` object, not the whole exported record.

  And the new `job_id` is what breaks things downstream — every [external orchestrator](/pipelines/external-orchestrators) reference, every `run-now` call, and anything pinned to the old number. Keep a source-to-target job ID map from this step; it is the same artifact the model and query migrations need for their own IDs. [`dbxmig bundle`](/templates/automation-toolkit) does this transformation for you, including turning the workspace-scoped IDs into variables.
</Callout>

## Migrating hundreds to thousands of jobs quickly

<Callout client:visible variant="tip" title="Bulk-export via Terraform, not one job at a time">
  At more than a handful of jobs, the export/import loop above is the wrong shape. The [Databricks Terraform Exporter](https://github.com/databricks/terraform-provider-databricks/blob/main/docs/guides/experimental-exporter.md) (an experimental feature of the `databricks/databricks` Terraform provider) bulk-exports jobs, clusters, notebooks and policies as importable Terraform in one run — including `-targetCloud`/`-nodeTypeMappingFile` for automatic cross-cloud node-type translation (Databricks' own guide states roughly 99.5% coverage; attributes with no target-cloud equivalent, like an AWS `instance_profile_arn`, are silently omitted rather than erroring — diff the plan, don't just apply it).

  Four behaviors change how you plan a bulk run, confirmed from the exporter's own guide:
  - **Jobs deployed via Databricks Asset Bundles are not exported at all** — re-deploy their bundle against the target instead.
  - **`-incremental` does not apply to jobs or clusters**, only notebooks and SQL objects — a re-export after source changes re-exports every job in full.
  - **`-services` filters and organizes output, it does not split it into per-team Terraform modules** — there's no flag for that.
  - **Exporter parallelism is tunable but low by default**: `EXPORTER_PARALLELISM` defaults to 15, `EXPORTER_WS_LIST_PARALLELISM` to 5, and most per-resource-type handlers default to 2 if unset — raise these explicitly for a large export rather than assuming the tool self-tunes.
</Callout>

<Callout client:visible variant="tip" title="For jobs/bundles specifically, a scripted bundle-init factory beats a giant exporter run">
  `databricks bundle init --config-file answers-<team>.json` runs fully non-interactively against a JSON answers file matching a `databricks_template_schema.json` — no manual prompts. For a job estate in the thousands, emit one small JSON per team/domain from your own job-ownership inventory and invoke `bundle init` once per file, rather than one exporter run covering the whole workspace. See [Asset Bundle custom templates](https://docs.databricks.com/aws/en/dev-tools/bundles/template-tutorial) and [Terraform patterns](/templates/terraform-patterns#factory-pattern-modules--whats-real-whats-stale).
</Callout>

<Callout client:visible variant="warning" title="What actually gates throughput at scale">
  The Jobs API itself is rarely the bottleneck — `/jobs/create` is rate-limited at 20 requests/second, `/jobs/runs/submit` at 35/s, and a workspace can hold 12,000 saved jobs and create up to 10,000/hour, all fixed ceilings. The real limits worth planning around: 2,000 simultaneously running tasks and 750 simultaneously running parent tasks per workspace (`Run job`/`For each` tasks excluded from both counts) — the concurrency ceiling that matters at cutover is per-workspace, not per-job. And if bundle deploys feel slow, check whether the deploying CLI is on the newer **direct bundle engine** (CLI 0.279.0+, default from CLI 1.3.0+, or set `DATABRICKS_BUNDLE_ENGINE=direct`) — Databricks states it deploys up to 40% faster than the classic Terraform-based engine.
</Callout>

<Callout client:visible variant="warning" title="A bundle-deployed job is locked from manual edits — by design">
  A job deployed through an Asset Bundle gets `edit_mode: UI_LOCKED` and cannot be switched to editable from the UI — this is deliberate Databricks behavior, not a bug to route around. Plan any post-migration hotfix path through the bundle source and a re-deploy, not a UI edit that will be silently blocked.
</Callout>

## Task reference rewrites

### Notebook paths

Workspace paths and repos may differ. Use a consistent naming convention and update task notebook paths.

<CodeBlock client:visible language="json" code={`"notebook_task": {
  "notebook_path": "/Shared/migration/<notebook>"
}`} />

### Warehouse endpoints

SQL tasks reference warehouse IDs. Recreate warehouses in target and update IDs.

### Catalog references

Update SQL and notebook code that hardcodes source catalog names. Use a naming standard or environment variables.


## Cloud-specific caveats

<Callout client:visible variant="warning" title="File-arrival triggers cannot be recreated identically cross-cloud">
  A file-arrival trigger is backed by a cloud-native event source — S3 event notifications on AWS, ADLS Gen2 events on Azure, GCS Pub/Sub notifications on GCP. Migrating a job with a file-arrival trigger across clouds means re-implementing the trigger against the target cloud's native event mechanism, not just pointing the same trigger config at a new path. Budget this as a redesign, not a config edit — see [external orchestrators](/pipelines/external-orchestrators) for the equivalent nuance on externally-scheduled triggers.
</Callout>

<Callout client:visible variant="warning" title="Recreating a job does not bring its run history with it">
  Exporting `jobs.json` and re-creating jobs in target captures the **definition** only. The new job gets a new job ID and starts with zero run history — the source job's past runs, durations, and failure rates stay in the source workspace and age out on Databricks' own retention window (60 days via the Jobs API/UI). If run history is needed for audit, SLA reporting, or an incident investigation later, pull it via `2.1/jobs/runs/list` (or `system.lakeflow.job_run_timeline`) and archive it before the source workspace is retired — see [known limitations](/troubleshooting/known-limitations) for the full list of history that doesn't carry over and how to log it.
</Callout>

## Scheduling freeze

During cutover:

1. Pause source jobs at the agreed freeze window.
2. Catch up target data to the last source commit or transaction.
3. Enable target jobs in dependency order.
4. Monitor the first target runs for failures.

## Validation

- Run every migrated job at least once in the target before cutover.
- Compare run times, output counts, and failure rates against recent source runs — there is no historical baseline in target to compare against, only what you capture from source before cutover.
- Verify notification delivery and alerting.
- Archive source run history if it's needed after cutover; don't assume it's retrievable from target later.

## Rollback

If a target job fails, re-enable the source job and investigate. Do not decommission source jobs until hypercare.

## Automation opportunity

- Store job definitions as code in a Git repository.
- Use CI/CD to deploy jobs to target environments.
- Script path and catalog rewrites across job JSON.
