# Workflows and jobs

Databricks Workflows is the native orchestrator for notebooks, Python, SQL, and DLT tasks. At any estate past a handful of jobs, migrating them one at a time through the CLI is the wrong shape — the [Databricks Terraform Exporter](https://github.com/databricks/terraform-provider-databricks/blob/main/docs/guides/experimental-exporter.md) or a scripted `bundle init` factory does the bulk-export/recreate mechanics; what's left for you to do by hand is rewriting cloud-specific references and deciding what genuinely can't be automated (file-arrival triggers, run history).

## Job components to migrate

| Component | Consideration |
|-----------|---------------|
| Task graph | Bulk-exported and recreated by the Exporter/bundle path below; validate dependencies survived |
| Cluster / job cluster | Map node types, runtime, access mode |
| Notebook tasks | Ensure notebooks exist in target workspace or repos |
| Python wheel tasks | Rebuild and publish wheels to target artifact store |
| SQL tasks | Rewrite warehouse endpoint and catalog references |
| DLT tasks | Recreate pipeline in target and update catalog paths |
| Triggers | Reconfigure schedule, file arrival, or continuous triggers |
| Notifications | Update email lists and webhook endpoints |
| Permissions | Replay job ACLs with mapped principals |

## The fast path: bulk-export via Terraform, not one job at a time

<Callout client:visible variant="tip" title="Terraform Exporter — the default for anything past a handful of jobs">
  The [Databricks Terraform Exporter](https://github.com/databricks/terraform-provider-databricks/blob/main/docs/guides/experimental-exporter.md) bulk-exports jobs, clusters, notebooks and policies as importable Terraform in one run, with `-targetCloud`/`-nodeTypeMappingFile` for cross-cloud node-type translation (~99.5% coverage; unmapped attributes like `instance_profile_arn` are silently omitted — diff the plan, don't just apply it).

  <CodeBlock client:visible language="bash" code={`export DATABRICKS_HOST=<SOURCE_WORKSPACE_URL>
export DATABRICKS_TOKEN=<TOKEN>

terraform-provider-databricks exporter \\
  -skip-interactive \\
  -listing=jobs,compute,notebooks,policies \\
  -targetCloud=aws \\
  -nodeTypeMappingFile=node-types.json \\
  -directory ./exported`} />

  Four things to plan around:
  - **DAB-deployed jobs aren't exported at all** — re-deploy their bundle instead.
  - **`-incremental` doesn't apply to jobs or clusters** — a re-export is always full.
  - **`-services` organizes output, it doesn't split it into per-team modules.**
  - **Parallelism is low by default** (`EXPORTER_PARALLELISM=15`, most handlers default 2) — raise it explicitly for a large export.
</Callout>

<Callout client:visible variant="tip" title="For jobs/bundles specifically, a scripted bundle-init factory beats a giant exporter run">
  `databricks bundle init --config-file answers-<team>.json` runs fully non-interactively. At thousands of jobs, emit one JSON per team/domain from your job-ownership inventory and invoke it once per file, rather than one exporter run over everything. See [Asset Bundle custom templates](https://docs.databricks.com/aws/en/dev-tools/bundles/template-tutorial).
</Callout>

<Callout client:visible variant="warning" title="Strip the server-owned fields before re-creating, or the create fails">
  A job exported from source carries `job_id`, `created_time`, `creator_user_name` — the target assigns its own. The new `job_id` breaks every [external orchestrator](/pipelines/external-orchestrators) reference and `run-now` call pinned to the old number — keep a source-to-target ID map. [`dbxmig bundle`](/templates/automation-toolkit) does this transformation for you.
</Callout>

<Callout client:visible variant="warning" title="What actually gates throughput at scale">
  The Jobs API is rarely the bottleneck (`/jobs/create` 20 req/s, 12,000 saved jobs, 10,000 created/hour). What matters is 2,000 simultaneous tasks and 750 parent tasks per workspace — a per-workspace ceiling, not per-job. If bundle deploys feel slow, check for the **direct bundle engine** (CLI 1.3.0+ default, or `DATABRICKS_BUNDLE_ENGINE=direct`) — Databricks states up to 40% faster than classic Terraform-based deploys.
</Callout>

<Callout client:visible variant="warning" title="A bundle-deployed job is locked from manual edits — by design">
  Gets `edit_mode: UI_LOCKED`, not switchable from the UI. Plan any hotfix through the bundle source and a re-deploy, not a UI edit that will be blocked.
</Callout>

## Extracting existing jobs as DABs, in bulk

<Callout client:visible variant="tip" title="databricks bundle generate job — one job's UI-created config into bundle YAML">
  For jobs that were built by hand in the UI and never lived as code, `databricks bundle generate job --existing-job-id <id>` reverse-engineers that job's live settings into a bundle-ready `resources/*.yml` plus a matching notebook/file layout — the step before you can `bundle deploy` it into target at all. It takes **one job ID per invocation**, not a bulk list, so at scale this is a loop over your job inventory, not a single command:

  <CodeBlock client:visible language="bash" filename="dabify-all-jobs.sh" code={`# job-ids.txt: one existing_job_id per line, from your asset inventory
while read -r job_id; do
  databricks bundle generate job --existing-job-id "$job_id" \\
    --profile source --key "job_$job_id"
done < job-ids.txt

# Review every generated resources/*.yml BEFORE deploying -- generate does not
# rewrite cross-cloud references (cluster node types, catalog names, warehouse
# ids) for you. Then, against the target profile:
databricks bundle deploy --profile target -t prod`} />

  `dbxmig bundle` (see [automation toolkit](/templates/automation-toolkit)) does the equivalent transformation from this toolkit's own workspace inventory in one pass, with cross-cloud rewrites and every schedule paused on arrival — prefer it when you already have that inventory; reach for the loop above when you don't and only need the bundle-ification, not the rewrite.
</Callout>

<Callout client:visible variant="tip" title="AI coding agents now ship first-class Databricks skills — `databricks aitools install`">
  Databricks' own CLI (`databricks aitools install`, documented under `dev-tools/cli/reference/aitools-commands`) installs Databricks-specific skills into a coding agent — Claude Code, Cursor, Codex CLI, GitHub Copilot, Gemini CLI, and others — so the agent can assess and rewrite job/bundle/SQL code with Databricks' own conventions built in, rather than a generic LLM guessing at Databricks-specific patterns. This is the successor to the `databricks-solutions/ai-dev-kit` project (1,900+ stars, Databricks-certified) — its skills are now installed straight through the CLI. For a migration specifically, this is where you'd point an agent at the loop above and have it draft the cross-cloud rewrites (node types, catalog names, warehouse IDs) per generated bundle file — still gated by the same review and reconciliation this page and [AI-assisted migration](/accelerators/ai-assisted-migration) already require, not a reason to skip them.
</Callout>

## Fallback: a handful of jobs, or nothing else fits

For a genuinely small job count, or a one-off job the Exporter/bundle path doesn't cover cleanly, the manual CLI loop is still a legitimate option — just don't reach for it as the default at scale:

<CodeBlock client:visible language="bash" code={`# Export all jobs from source workspace.
# List endpoints paginate -- always check the count against the workspace UI
# before trusting the export, or you migrate a page and report success.
databricks jobs list -o json > jobs-raw.json
jq 'if type=="array" then . else .jobs end | length' jobs-raw.json

jq 'if type=="array" then . else .jobs end | .[] | {job_id, settings}' \\
  jobs-raw.json > jobs.json

# Create a job in the target workspace after editing the JSON.
# The flag is --json with an @path, not --json-file.
databricks jobs create --json @job-target.json`} />

## Task reference rewrites

Whichever path recreates the job definitions, the same references need rewriting before they run correctly in target:

### Notebook paths

Workspace paths and repos may differ. Use a consistent naming convention and update task notebook paths.

<CodeBlock client:visible language="json" code={`"notebook_task": {
  "notebook_path": "/Shared/migration/<notebook>"
}`} />

### Warehouse endpoints

SQL tasks reference warehouse IDs. Recreate warehouses in target and update IDs.

### Catalog references

Update SQL and notebook code that hardcodes source catalog names. Use a naming standard or environment variables.


## Cloud-specific caveats

<Callout client:visible variant="warning" title="File-arrival triggers cannot be recreated identically cross-cloud">
  A file-arrival trigger is backed by a cloud-native event source — S3 event notifications on AWS, ADLS Gen2 events on Azure, GCS Pub/Sub notifications on GCP. Migrating a job with a file-arrival trigger across clouds means re-implementing the trigger against the target cloud's native event mechanism, not just pointing the same trigger config at a new path. Budget this as a redesign, not a config edit — see [external orchestrators](/pipelines/external-orchestrators) for the equivalent nuance on externally-scheduled triggers.
</Callout>

<Callout client:visible variant="warning" title="Recreating a job does not bring its run history with it">
  Neither the Exporter nor a manual export/recreate captures anything but the job **definition**. The new job gets a new job ID and starts with zero run history — the source job's past runs, durations, and failure rates stay in the source workspace and age out on Databricks' own retention window (60 days via the Jobs API/UI). If run history is needed for audit, SLA reporting, or an incident investigation later, pull it via `2.1/jobs/runs/list` (or `system.lakeflow.job_run_timeline`) and archive it before the source workspace is retired — see [known limitations](/troubleshooting/known-limitations) for the full list of history that doesn't carry over and how to log it.
</Callout>

## Scheduling freeze

During cutover:

1. Pause source jobs at the agreed freeze window.
2. Catch up target data to the last source commit or transaction.
3. Enable target jobs in dependency order.
4. Monitor the first target runs for failures.

## Validation

- Run every migrated job at least once in the target before cutover.
- Compare run times, output counts, and failure rates against recent source runs — there is no historical baseline in target to compare against, only what you capture from source before cutover.
- Verify notification delivery and alerting.
- Archive source run history if it's needed after cutover; don't assume it's retrievable from target later.

## Rollback

If a target job fails, re-enable the source job and investigate. Do not decommission source jobs until hypercare.

## Automation opportunity

- Store job definitions as code in a Git repository.
- Use CI/CD to deploy jobs to target environments.
- Script path and catalog rewrites across job JSON.
