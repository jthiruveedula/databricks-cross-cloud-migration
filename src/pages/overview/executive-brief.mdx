# Executive brief

For teams moving Databricks **from one cloud to another** — AWS ↔ Azure ↔ GCP. In-place Unity Catalog upgrade or same-cloud region move instead? Start at [remote governance vs. migration](/overview/remote-governance-and-when-not-to-migrate) before committing to a physical move.

<Callout client:visible variant="warning" title="The case in one sentence">
This is rarely about the data — Delta and object storage move through well-trodden patterns. It's about **identity, storage layout, networking, and governance** landing in a target account your teams actually own. Budget the schedule for everything around the data, not the data itself.
</Callout>

## The decision gate — answer this first

**Does the business driver actually require moving data?** Unity Catalog federation governs and queries data in place, across clouds, no physical move. Governance-only is often weeks; physical migration is quarters.

| Driver | Path |
| --- | --- |
| Single pane of governance, compliance boundary, new-team read access | Remote governance |
| Egress cost, region latency, cloud mandate, sovereignty boundary | Physical migration |

## Three risks that blow timelines

1. **Uninventoried dependencies** — an orphaned notebook calling a table behind a DBFS mount. Discovery is cheap insurance.
2. **Identity done late** — the longest pole. Start it in Foundation, not Cutover.
3. **Legacy Hive metastore debt** — every workspace-local table adds UCX-assisted upgrade work inside the migration.
